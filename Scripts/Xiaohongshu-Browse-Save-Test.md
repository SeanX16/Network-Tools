# 小红书浏览与保存测试 v1（Quantumult X）

独立测试版，日期：2026-11-11。用于验证能否减少浏览时的高清资源强制加载，同时保留高清保存。尚未在 iPhone 上验证，不能把“提供多个候选”视为已经实现播放自适应，也不能保证长按保存一定取最高画质。

## 安装与回退

测试订阅：

https://raw.githubusercontent.com/SeanX16/Network-Tools/main/Scripts/Xiaohongshu-Browse-Save-Test.conf

1. 在 QX 的重写资源中添加上述链接。停用小红书整合版、原版、独立高清保存版及旧测试版，只启用本测试版；不用删除原订阅。
2. 更新资源和脚本，保持重写、MitM 和证书信任开启。首次功能测试关闭 HTTP 抓取，保持与日常使用一致。
3. 从后台退出小红书，再打开笔记。旧页面和 App 媒体缓存可能影响结果；测试此前看过的同一条笔记时，建议先在小红书自己的设置中清理缓存，再退出重开。QX 的“清除缓存”任务只清理链接文本，不能清理小红书媒体缓存。
4. 如出现图片空白、视频卡住或保存失败：停用本测试版，重新启用原整合版，退出小红书再重开。必要时按相同方式清理 App 缓存再对照。

## 本版具体改变

- 静态图片：合法完整 `fileid` 对应的源地址只写入 `original`。`url`、`url_size_large`、`url_multi_level`、`url_8k`、`hd_img`、`need_load_original_image` 及宽高元数据原样保留。App 是否在保存时读取 `original`、浏览时是否预取它，需要实测。
- 实况及缺少合法 `fileid` 的图片：图片数据保持接口原样，不执行原版 2160 放大。实况保存接口的原有逻辑保留。
- 测试版不读取或修改 `fmz200.xiaohongshu.imageQuality`，避免历史画质设置干扰；切回正式版后仍使用原设置。
- v4 视频：保留所有符合已知 MP4/AAC 兼容条件的 HEVC/H.264 候选，保持组内原顺序，不再锁定单个高清流。优先沿用保留下来的原默认；若有多个默认，只取原列表遍历顺序中的首个。若原默认被过滤，选择较低分辨率兼容候选作为默认起播版本，同分辨率优先 HEVC，再取较低码率。
- 视频保存接口缓存仍按最高分辨率、同分辨率 HEVC 优先、同编码较高码率选取，保留完整签名 URL。只有实际经过 v10 保存接口时，这份独立缓存才会被使用。
- 无兼容候选或 DRM 标记不符合条件时，保留原视频列表，不缓存替代地址。仍沿用每次非空视频信息流覆盖缓存的机制。
- 其余去广告、净化、按钮和权限处理、实况保存及评论规则沿用整合版。测试版和正式版共用四项 QX 链接缓存，切换后应重新打开目标笔记生成新缓存。

这不是完整恢复原生播放：非兼容类型仍被过滤。没有低清兼容候选时，也无法凭空增加低清版本。QX 的信息流重写不直接知道 App 是在浏览还是准备保存，不能感知相册写入失败并自动重试。

## 第一轮：先验证功能

### 图片

1. 用之前提供的三图笔记，先只正常浏览、翻图，不点任何“原图”入口，观察加载是否正常。
2. 在相同等待时间（例如 5 秒）后长按保存第一张，到系统相册的信息页查看像素尺寸。目标是 **3072×5461**；1440×2560、2160×3840 或 2814×5000 都不是此前核对到的完整源尺寸。
3. 再保存第二、第三张，对应源尺寸分别为 **3456×6143**、**3072×5461**。这些是此前实际下载源文件核对的尺寸，不是本测试版已通过的保存结果。
4. 如果普通长按保存不是源尺寸，而 App 提供“原图”入口，再点原图后重存一次，记录两次差异；如果没有该入口，跳过此项。另找一条新的图文和一张实况确认正常显示、保存及实况播放。

### 视频

1. 重开此前验证过的《意想不到的love》，先看播放是否正常，固定等待 5 秒后长按保存。
2. 查看相册中的分辨率、编码（如果信息页显示）、水印及声音。此前已成功保存过 **1080×1920 HEVC、无水印**，本版应以此作为对照目标。
3. 再选两条不同视频复测。如果看着流畅但保存成低清，也应记为“保存画质未达标”，不能算全部通过。

## 第二轮：比较浏览流量与弱网表现

先完成上述功能测试，再分别在正式版和测试版下比较同一批笔记。每轮只启用一个订阅，使用相同网络、相同浏览时长（例如每条 10 秒），只浏览不保存、不手动点原图，并记录 QX 网络活动中对应媒体连接的流量。注意已有连接计数可能包含先前流量，不能直接比较累计总数。

每轮前用同样方式清理小红书缓存并退出重开，尽量避免上一轮下载的媒体被复用；否则“第二次加载更快”不能证明脚本省流量。网络活动流量只能作辅助对照；精确判断选中的媒体地址及尺寸需要后续按笔记分析抓包。

正常网络比较后，再在同一种较差网络条件下观察首图/首帧等待、卡顿和清晰度变化；不要一轮 Wi-Fi、一轮蜂窝后直接归因于脚本。若原默认本身就是高清，本版仍可能高清起播，需要 App 真正使用较低候选才能降低流量。

## 日志和反馈

在 QX 网络活动的脚本记录中找 `xhs-browse-save-test.js`，搜索 `[浏览保存测试 v1]`：

- `图片 original=3/3；预览字段与加载标记保持原样`：表示字段已改写，不表示已经保存成功。
- `视频候选=...；默认=...；保存接口候选=...`：表示提供给 App 的候选与默认，不是 App 实际下载结果。
- `收到 v10 保存响应`：此次执行确实命中了该保存接口。
- `v10 已替换为缓存的最高画质兼容地址`：缓存中的笔记匹配成功，已替换下载地址。仅出现上一条而没有此条，说明未命中可用缓存。
- 有视频信息流日志但保存时没有 v10 日志：本次没有观察到该重写路径执行；不能仅凭缺少日志断言 App 一定没有发任何保存请求。
